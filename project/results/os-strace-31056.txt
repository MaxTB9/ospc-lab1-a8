== How to read it ==
- 82 % of the time in system calls is waiting, not work: futex (50 %, locks and the queue
  between the main process and the workers) and wait4 (37 %, the main process waiting for the
  workers to finish). Neither uses CPU while it waits.
- Nothing points at I/O: read and write together are under 1.1 % of the time and write is called
  only 531 times (the small CSV and the printed lines). No sockets or network calls appear.
- Most of the other calls (openat, stat, mmap, fstat, read, lseek, close: about 28,000 of the 39,000
  calls listed) look like Python and Numba start-up, loading modules and the Numba cache, in the
  main process and the 4 workers. The errors on openat, stat and ioctl are failed lookups while
  Python searches its paths and checks whether a file is a terminal; they are harmless.
- futex: 2610 calls for 256 runs is about 10 per run, the cost of handing each run to a worker
  through the queue (chunk size 1). That cost is small next to a run (about 9 ms) but is the part
  that grows with the number of runs.
- The 100,000 annealing steps of a run make no system calls: the solver runs inside Numba.
  This table cannot separate start-up from solving; a run with more runs would show whether the
  counts stay the same.
