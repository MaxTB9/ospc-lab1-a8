## Correctness, reproducibility and OS behaviour (Person 4)

**Testing.** Our versions are only comparable if they make the same moves. The Python, NumPy and Numba solvers all read one pre-generated random stream per run, which depends on the run number and never on the worker. `tests/test_equivalence.py` checks that the Numba timetable gives every exam one slot, has no clashes and keeps a running score equal to a from-scratch score. It then checks that the three versions end with the same accepted moves, score and timetable, for fixed length and with patience. A deliberately broken solver makes it fail; it passes on the cluster. In the scaling jobs the checksum of all timetables was identical (1499360352) for 1 to 64 workers.

**Cores.** `lscpu` and the CPU pairs (CPU 21 with CPU 277, checked on the node) show that the 32 CPUs of job 30212 were 16 physical cores, and the 64 CPUs of job 30974 were 32 cores. Up to 32 workers each had a core (speedup 30.7, efficiency 0.96); 64 workers added only 19 %. Requesting `-c 4` gave only 2 cores, so 4 workers took 16.9 s, not 9.25 s.

**CPU-bound.** For 4 workers, `/usr/bin/time -v` reported 392 % CPU, 2 % system time and no swaps; `sacct` agrees on CPU time (68.7 s). In `strace -c`, 87 % of system-call time is `futex` and `wait4`, which are waits, and under 1.1 % is `read` and `write`. Whole-job CPU efficiency is low (8.2 % and 6.2 %) because each job runs the worker counts one after another; inside a run, workers are 98 to 100 % busy.
